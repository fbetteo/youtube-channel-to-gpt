# Jobs, credits, and payments

## Job lifecycle

- Normalize/deduplicate available videos with `youtube_service.normalize_videos_for_job` before reserving credits.
- Create durable transcript jobs through `hybrid_job_manager` / `JobManager`. Reservation and job/video insertion can share a database transaction. Accepted paid work must not silently become file-only after a database error.
- Persist discovery through `db_youtube_transcripts/discovery_job_manager.py` before scheduling it. Distinguish discovery, transcript, and batch IDs.
- `youtube_service.prefetch_and_dispatch_task` coordinates metadata/dispatch. Lambda uses `InvocationType="Event"` and alias `prod`: invocation acceptance does not mean transcript completion. `max_concurrent` currently does not impose a dispatch semaphore.
- Workers upload text under `{user_id}/{job_id}/{video_id}.txt` in S3, plus the caption segments as `{video_id}.json` beside it (used for non-txt download formats; see [api.md](api.md)), try SQS result delivery first, and fall back to HTTP callbacks when available.
- Worker transcript cache: before calling YouTube, the worker reads `transcript-cache/{video_id}/{requested_language|auto}.json` from the same bucket and reuses it. `TRANSCRIPT_CACHE_MAX_AGE_DAYS` (Lambda env): unset (default) reuses entries forever; `N` re-fetches and overwrites entries older than N days; `0` never reuses. Fetches always write it back, and no code deletes entries; clean the prefix in S3 directly if needed. Cache read/write errors fall back to a live fetch. A cache hit completes and is charged like any other completed video. Single-video paths read and write the same objects (see the shared transcript cache in [api.md](api.md)); the worker has no database access, so it sends the index row as `cache_entry` in its completion message (with `hit` when it reused the entry) and `job_result_processor.process_video_completion` upserts it with `source='job'`. The message omits it when the worker's cache write failed; older workers never send it.
- SQS requires a separate `src/sqs_result_consumer.py` process. Both delivery paths use `src/job_result_processor.py`; preserve shared processing and duplicate-result handling.
- Timeout, cancellation, dispatch failure, and late results have distinct paths. The only timeout is a periodic sweep (`run_stale_job_sweeper`) that reconciles active jobs with no progress for `JOB_TIMEOUT_MINUTES`, including jobs orphaned by an API restart; large jobs that keep receiving results are not cut off. The worker bounds its own fetch to the Lambda's remaining time minus `DEADLINE_SAFETY_SECONDS` and reports a retriable `DeadlineExceeded` failure instead of being killed silently. Lambda timeout should therefore stay well above that margin. Cancelled jobs ignore late results and preserve completed downloads. Inspect terminal accounting in `JobManager` before changing it.

## Credits and database

- Single authenticated raw downloads deduct one credit before the attempt.
- Bulk jobs reserve credits for accepted videos. Completed transcripts and non-retriable worker failures (no captions, unavailable/private video) consume credits. Retriable failures (proxy blocks, network errors, worker deadline) are our side and are not charged; a missing `retriable` flag is treated as chargeable for older workers; unprocessed work can be refunded during finalization/cancellation. A failure does not automatically mean a refund. Videos with no worker result before the job timeout (throttling, crash, lost message) are marked failed but not charged, so finalization refunds them.
- `JobManager` owns transactional progress, terminal transitions, cancellation, and refunds. Keep balance/job accounting consistent and preserve protection against repeated results or finalization.
- The asyncpg pool and transaction helper live in `db_youtube_transcripts/database.py`. Transactional locks/updates prevent concurrent workers applying the same progress/balance change independently. Legacy synchronous connections also exist.
- Schema/migration entry points: `db_youtube_transcripts/schema.py`, `schema_api_keys.py`, `migration_*.py`. Review execution effects before running against a configured database; code changes do not migrate deployed tables.

## Payments

Checkout/webhooks live in `src/transcript_api.py`. Pricing is a monthly subscription plus top-ups:

- **Stripe objects** come from `scripts/stripe_setup.py` (dry run unless `--apply`; `--test` uses `STRIPE_SECRET_KEY_TEST_TRANSCRIPTS`). Edit its `PLANS`/`TOPUPS` and re-run to change prices; active prices on its products that are no longer configured are archived. Code references prices by `lookup_key`, never `price_...` IDs; each price carries `metadata.credits`, `metadata.kind` (`plan`/`topup`) and `metadata.project`. Changing an amount creates a new price that takes over the lookup key; existing subscribers stay on the old price. The script also manages a dedicated Customer Portal configuration (`STRIPE_PORTAL_CONFIGURATION_ID`) and can add the needed events to the existing webhook endpoint (`--webhook-url`). Keep the frontend's `components/PricingComponent.tsx` amounts in sync.
- **Plan**: `POST /payments/create-subscription-checkout {lookup_key}` (409 when already subscribed). The user is linked through `subscription_data.metadata` (`project`, `user_id`). Credits are granted per paid invoice, not on checkout.
- **Top-ups**: `POST /payments/create-checkout-session {lookup_key, quantity}` requires an active subscription (403 otherwise). There is one top-up price; `quantity` (1-100, default 1) buys that many units, granting `quantity` x the price's credits as one lot. The session carries `metadata.kind=topup` and the total `metadata.credits`. Legacy pack `price_id`s in `PRICE_CREDITS_MAP` are still accepted without a subscription for old clients.
- **Portal**: `POST /payments/portal` returns a Stripe Customer Portal URL (cancel at period end, card, invoices).
- **Balance**: `GET /user/credits` returns `credits` split into `subscription_credits`, `topup_credits` with `topups[{credits, expires_at}]` (latest expiry first), `permanent_credits`, and the active `subscription` (status, lookup_key, monthly_credits, cancel_at_period_end, current_period_end).

**Credit expiry** (`src/credit_ledger.py`). `user_credits.credits` stays the single spendable balance, so reserve/deduct/refund code is unaware of subscriptions. The balance is split into layers:

- Expiring lots (`credit_lots` rows with `expires_at`): one `monthly` lot per plan period, expiring at the Stripe period end, and one `topup` lot per purchase, expiring 30 days later or when the plan ends, whichever comes first. **Credits that expire soonest are spent first**, so after a renewal an older top-up is used before the fresh monthly credits.
- Permanent credits (`user_credits.permanent_credits`): welcome credits, legacy packs, and the balance held when first subscribing. They never expire and are spent last.
- Unassigned: whatever the total holds beyond those (a non-subscriber's balance, or refunds of credits whose lot is gone). Spent first.

Stored lot sizes are upper bounds, because spending only lowers `credits`; `split()` derives each layer's real size from the total, filling permanent credits first and then lots from the latest expiry. So a refund refills the lowest spent layer first. Writes lock the `user_credits` row, normalize the layers, apply one change, and store the new total:

- `start_period` on `invoice.paid` (`billing_reason` `subscription_create` or `subscription_cycle`): replaces the monthly lot with this period's credits, expiring at the subscription's `current_period_end`, and drops unassigned credits. The first period turns unassigned credits (whatever the user held) into permanent credits, so existing rows need no backfill. Monthly lots are never expired on a timer: a renewal replaces them and the plan ending removes them, so credits survive while Stripe retries a late payment (`past_due`).
- `grant_topup` (checkout `metadata.kind=topup`) adds a 30-day lot; `grant_permanent` (legacy packs, no `kind`) adds permanent credits.
- `end_subscription` when a subscription is no longer `active`/`trialing`/`past_due`: removes monthly, top-up and unassigned credits, unless another subscription of the user is still active. A user with an ended plan keeps only permanent credits, so paid actions fail with insufficient credits.
- Top-ups past their date are removed by `run_topup_expiry_sweeper` (API startup, every 5 minutes; safe across workers because of the row lock) and on `GET /user/credits`. Between expiry and the sweep, spending can still use them for up to 5 minutes.

`GET /user/credits` reports unassigned credits as permanent without an active plan (existing users have `permanent_credits = 0` stored until their first plan period) and as subscription credits with one.

`past_due` keeps credits while Stripe retries the card. Subscription and invoice events re-fetch the subscription from Stripe (`_sync_stripe_subscription`), so event order and the endpoint's API version do not matter, and store it in `user_subscriptions` (one row per Stripe subscription). Webhook events needed: `checkout.session.completed`, `invoice.paid`, `customer.subscription.created|updated|deleted`. Schema: `db_youtube_transcripts/migration_add_subscriptions.py`. No annual plans or plan switching yet.

Keep frontend checkout payloads, referral metadata, and redirect URLs aligned. Browser success pages do not grant credits. For one-time payments the webhook grants credits on `checkout.session.completed` (ignored for `mode=subscription`) only when `payment_status` is `paid` or `no_payment_required` (100%-off promotion codes). Each Checkout session or subscription invoice is recorded in `stripe_checkout_credits` (`session_id` holds the session or invoice ID) in the same transaction as the credit grant, so redelivered events return `duplicate` without adding credits. That table comes from `db_youtube_transcripts/migration_add_stripe_checkout_credits.py`; until it exists, the webhook returns 500 and Stripe retries.

Relevant tests: `tests/test_playlist_job_lifecycle.py`, `tests/test_discovery_job_manager.py`.
